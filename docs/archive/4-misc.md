## 五、§7-B1/B2 STEP 0 探针明细与推理（v6.36 从主文件搬入 · 数字**冻结**）

> 搬入原因：主文件逼近 §10-14 的 100k 硬指标。主文件 B2 只留「数字表 + 三句改写 + 指向 D 节」；
> **"当年为什么这么定"的完整原文**在这里。

**探针表（原始）**

| 探针 | 测法 | 实测 | 全市场外推 | 结论 |
|---|---|---|---|---|
| **P1a** 单文件读 | 200 只 × 2 轮 | 全列 **2.0 ms/只**（热）· 投影 7 列 1.9 ms | ~11 s | ⚠ **列投影几乎不省（4%）**：文件太小（中位 0.12 MB），**打开开销主导** |
| **P1b** 目录级一次扫 | `pyarrow.dataset` 投影 | **174 ms / 368 只（0.46 ms/只）** | **~2.6 s** | ✅ 一次扫比逐个读快 ~4× ⇒ 用它 |
| **P1c** 只读尾部窗口 | `filters` 行组裁剪 | **8.6 ms/只（反而更慢）** · **row group 全部 = 1** | — | ❌ **无裁剪余地**，这条优化作废 |
| **P2** 宽度表构建 | `dataset` → `pivot_table` ×3（close/volume/amount） | 载入 177 ms + 宽表 **950 ms**；内存 **34 MB（f64）/ 17 MB（f32）** | 载入 **2.6 s** + 宽表 **~14 s**；内存 **499 MB（f64）/ 250 MB（f32）** | ⚠ `pivot_table` 是热点（约占宽表成本 85%）⇒ STEP 1 优化目标 |
| **P2b** 宽表稀疏度 | close 列 NaN 率 | **39.7%** | 更高（IPO 日期更分散） | 必须走**三态**；内存按 f32 预算 |
| **P3a** 计算·引擎逐只 | 120 只 × `execute_programs`（MA20+EMA12/26+CROSS） | **1.60 ms/只** | **~8.6 s** | ✅ **引擎本身不慢**（全市场 < 10 s） |
| **P3b** 计算·宽表向量化 | 同语义 pandas（rolling/ewm） | **0.409 ms/只** | **~2.2 s** | 加速比仅 **~4×** |
| **P3c** 一致性 | 两路逐位比对 | **按标的日期取行 → 0 差异**；按位置截断 → 86–168 处假不符 | — | ✅ **语义等价**，但**对齐方式必须正确** |

**三条由实测得出、会改写原设计的结论（原文）**

1. **❌ "5000+ 次文件打开是主要成本"（B 节的原假设）被推翻** —— 全市场载入约 **2.6 s**，
   且列投影（省 4%）与尾部窗口（row group=1）**都救不了**。
   ⇒ **"落盘面板 `kline_panel`"的首要理由（省 IO）不成立**，建议降级为
   **"会话内存面板（scan-time load）"**：一次载入 → 内存宽表 → 用完释放。
   省掉：落盘 ~430 MB + 数据管理页分组改造（方案 B）+ 增量/重建 + 缓存失效逻辑。
   ⚠ 这是**简化**不是"少做"：**三态、粗筛漏斗、与数据管理的联动（5 条）全部保留**；
   且缓存**进一步只存"结果矩阵"而非价量宽表**（内存 22 MB vs 500 MB，见 **D3**）。
2. **✅ 真换手率 / 流通股本其实已经可得（意外发现）**：`kline_daily` **已含
   `outstanding_share`（流通股本，股）与 `turnover`（换手率，**小数**：0.0093 = 0.93%）**，
   覆盖 **362/368（98.6%）** —— 来自新浪源 `stock_zh_a_daily` 的**透传列**
   （`_normalize_ohlcv` 只 rename、不裁列）。
   ⇒ 原"换手率本轮不做、用相对量替代"**应改为可用**；但必须：① 兜底源（东财）没有这两列 ⇒
   该股走**三态"数据不足"**；② 展示按用户量纲 **×100 显示为 %**；③ 这两列**不在任何 schema 常量里**
   （`OHLCV_COLUMNS` 只有 6 列）⇒ 属**隐性依赖**，必须显式登记，否则将来一次列裁剪就会**静默消失**。
3. **⚠ 复权"一次到位"遇到现实约束**：`kline_daily_raw`（不复权）**只有 1 只** ⇒
   "面板存不复权 + 复权因子（qfq ÷ raw）"的因子**几乎算不出来**。需二选一：
   (a) 先把 raw 分区备齐（数据管理「全市场扫描就绪」预设正好干这个）；
   (b) 本轮**只用前复权一种口径**并在界面明示（数据现成、覆盖 98%+）。

**另两条必须登记的数据健康问题（原文 · 已各自成节 ⇒ 见 §9.1 / §9.2）**

- **同一分区列结构不一致**：`kline_daily` 混入 ① 兜底源（东财）透传的**中文列**
  （`股票代码`/`成交额`/`振幅`/`涨跌幅`/`涨跌额`/`换手率`，各 1 只）；② **期货列**
  （`持仓量`/`动态结算价`，5 只期货标的）。
  ⇒ 扫描读列**必须按"列是否存在"裁剪 + 缺列走三态**，**禁止假设 schema 统一**。
  （分钟线路径有 `out[keep]` 列裁剪、**日线没有** —— 不对称，属可修的小债。）
- **`shift` / `REF` / `CROSS` 的跨空洞语义**：宽表按**全局交易日历**对齐时，标的缺数据日
  （停牌/未下载）会被 `shift(1)` 跨过 ⇒ 与"逐标的序列"（引擎口径）在边界可能不一致
  （实测 000021 有 31 个空洞日 ⇒ **4/4022（0.1%）不符**）。
  ⇒ STEP 1 必须定口径（二选一）：**(a) 向量化时"按列跳 NaN"做 shift**（成本 ≈ 0.5–2 s/全市场，可接受）
  或 **(b) 显式声明"扫描以全局交易日历对齐"** 并登记差异 —— **不许默默不同**。

**P4 · 端到端标杆（v6.43 从主文件 B3 搬入 · 数字冻结）**

实测环境：本机 368 只 / 90.1 万行 / 最新交易日 **2026-09-18**。

| 环节 | 实测 | 全市场外推（×14.7） |
|---|---|---|
| 载入（`dataset` 一次扫） | 189 ms | 2.8 s |
| 按标的分组 | 159 ms | 2.3 s |
| 粗筛漏斗 | **37 ms** ⇒ 候选 354/368 | 0.5 s |
| 精算（引擎逐只 × 354） | **1379 ms（3.90 ms/只）** | **20.2 s** |
| **端到端合计（首次冷扫）** | **1.79 s** | **≈ 26 s** |
| 会话缓存命中（切日期 / 切粗筛） | **0.03 ms/次** | 同量级 |

- **M2 三态实测**（2026-09-18）：命中 **11** · 未命中 **273** · **数据不足 84** · 有效样本 **354/368**
- **M3 广度实测**（近一年 234 个交易日）：最新 **11** 只（3.1%）· 中位 **7**（2.0%）· 最高 36 · 最低 1

**两条新发现（含对当时判断的修正）**

1. **⚠ 精算单只耗时比 P3 高 2.4×（3.90 vs 1.60 ms/只）** —— 差异**不在引擎**，而在 P4 里用
   **逐行 Python 累加逐日家数**（≈ 90 万次迭代）⇒ STEP 1 改"日期→整数索引 + `np.bincount`"。
2. **⚠ "漏斗能让精算量降一个数量级"不成立** —— 实测只砍 14/368（3.8%）；漏斗是**廉价保险**
   （负责"数据不足"的正确归因）但不能指望它救性能。

**当时的验收标杆**（后被 STEP 6 复核替代）：全市场首次扫描 ≤ 20 s；缓存切日期 ≤ 50 ms；
三态必显有效样本数。**STEP 1 复核（v6.34）**：368 只 2.60 s（7.06 ms/只）⇒ 外推 ≈38 s 高于标杆，
差额在 per-symbol 固定开销（`prepare_frame` 拷贝/掩码/循环）—— 性能对账三项登记在案；
最终 **STEP 6（v6.39）复核后决策：接受引擎路径，STEP 7 暂不排期**（见主文件 §7-B1/B2 G 节）。

## 6.5 市场回测·升级迭代路线（阶段 A/B/C 已落地，远期排期）

> 2026-09 定稿的产品口径：**信号语义 = 多条件满足计数**，OR/AND 只是"至少N"的两个特例，
> 不做传统意义上的单一"事件"二分。以下阶段由用户分期批准，逐批实施。

- **[x] 阶段 A（已落地）** —— 静态多条件信号：
  - A-1 `COUNT_TRUE` 计数原语（runtime 注册表，变参 1~99）。
  - A-2 多函数段共享变量池（`execute_programs`）——覆盖"MACD金叉 + KDJ<20 + 自研>20"。
  - A-3 UI 条件组 Gate（多行积木 + 全部/任一/至少N）——覆盖"多个卖点任一满足就卖"。
  - A-4 策略快照结构升级 + 老档兼容读取。
- **[x] 阶段 B（已落地）** —— 引擎风控离场器（治"指标滞后、盈利单变亏"的**动态**痛点）：
  - B-1 `core/backtest.py`：`normalize_risk()` 归一百分比口径；`BacktestTrade.exit_reason` 记录
    离场来源（`signal`/`stop_loss`/`take_profit`/`trailing`/`max_bars`/`force_close`）。
  - B-2 引擎硬性规则（与信号正交）：固定止损/止盈/移动止盈基于当日 low/high **盘中触发即离场**
    （触发价=预设线，跳空越线则按开盘价，不占便宜）；下沿止损与移动止盈同根都触及取更高线先成交；
    `max_bars` 第 N 根收盘仍持仓则**当日收盘强平**；**硬规则优先于卖出信号**；净值/成交记录不变形。
  - B-3 `BacktestEngine.run(..., risk=dict)` 全零=关闭，默认行为与旧版完全一致（回归已验）。
  - B-4 UI：下区新增「🛡 风控离场」参数行（最长持仓/固定止损/固定止盈/移动止盈，0=关闭）；
    成交明细表新增「离场原因」列（按原因着色 + tooltip）。
  - B-5 `strategy_store`：策略 payload 新增 `risk` 字段；`_signature` 计入风控
    （全 0 等价旧档空字段，签名兼容已验证）。
- **[x] 阶段 C（已落地）** —— 大盘/指数 regime 门控（"不能把个股与大盘分离"）：
  - C-1 `data/akshare_feed.py`：新增 `fetch_index_daily(symbol, min_date)` 新浪指数接口
    （`ak.stock_zh_index_daily`，代码须带前缀如 `sh000001`/`sz399001`，附 `INDEX_PRESETS` 预设表
    与 `is_index_symbol` 校验）；数据落盘数据湖 **`index_daily` zone**。
  - C-2 `core/utils.align_by_date()`：把指数侧(外部日历)序列对齐到个股交易日轴
    —— reindex + ffill（指数停牌日沿用前值），前导空洞按 0 兜底。
  - C-3 UI ③「大盘/指数 regime 门控」卡（可折叠）：启用勾选 + 指数下拉/手输 +
    买卖两个指数 Gate（`gate_index_buy` 买入许可 / `gate_index_sell` 卖出破位）。
    指数 Gate 变量池 = 同一批函数段的 `IDX_` 前缀变量（同一段函数既算个股也算大盘）。
  - C-4 回测链路零引擎改动：指数函数段在大盘上求值 → 指数 Gate 表达式求布尔 →
    `align_by_date` 对齐 → 门控列 `IDX_GATE_BUY/SELL` 拼入个股 df →
    最终表达式 = 原买入 `AND` 许可门控 / 原卖出 `OR` 破位门控。
  - C-5 数据就绪链：先指数后个股（各自本地缺则 QThread 同步后再续跑）；
    `_signature` 计入指数门控（未启用/条件空等价旧档空字段）。
  - 边界纪律：指数求值失败（函数段依赖个股独有列）→ 明确提示，不静默放行。
- **[ ] 远期** —— 组合级多标的引擎（指数择时后全市场挑股 + 资金分配）= 全新模块，勿并入 M1。
